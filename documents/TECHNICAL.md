## 1. Идентификация проекта

**Проект:** SLADE 3 Mobile  
**Назначение:** Android-приложение для просмотра и редактирования
ресурсных архивов семейства Doom с использованием SLADE 3 в качестве
нативного бэкенда для работы с архивами и ресурсами.

**Текущая база SLADE:** SLADE 3.3.0 Beta 2

Это не буквальный порт настольного приложения на Android.
Пользовательский интерфейс Android, работа с файлами, жизненный цикл,
многопоточность и интеграция с платформой реализованы нативно для
Android, тогда как выбранные компоненты SLADE без графического
интерфейса повторно используются через C++.

## 2. Среда разработки

Проект содержит один модуль Android-приложения:

```text

```

Конфигурация Gradle разделена между:

```text

```

В приложении используется **View Binding**, а не Jetpack Compose.

## 5. Система нативной сборки

Нативный код собирается через Android Gradle Plugin + CMake + NDK.

Точка входа:

```text
app/src/main/cpp/CMakeLists.txt
```

В результате нативной сборки создаются:

```text
slade_core   — STATIC
myapplication — SHARED
```

`slade_core` содержит выбранные headless-компоненты SLADE для работы с
архивами и данными без настольного UI. Компоненты, сильно зависящие от
wxWidgets/OpenGL и desktop GUI, намеренно исключены.

`myapplication` — JNI-мост, загружаемый из Kotlin:

```kotlin
System.loadLibrary("myapplication")
```

## 6. Интеграция исходного кода SLADE

Исходный код SLADE хранится непосредственно в проекте по пути:

```text
app/src/main/cpp/third_party/SLADE/
```

Текущая схема:

```text
Исходный код SLADE
    ↓
выбранные компоненты без desktop UI
    ↓
слой совместимости с Android
    ↓
slade_core
    ↓
JNI-мост
    ↓
Kotlin Android UI
```

Android-специфичный код совместимости находится в:

```text
app/src/main/cpp/compat/
```

Слой совместимости должен оставаться тонким и не превращаться во вторую
независимую реализацию SLADE.

## 7. Текущий охват архивных форматов

Текущий нативный слой ориентирован на **WAD**.

`ZipArchive.cpp` намеренно исключён, поскольку настольная реализация
зависит от desktop/wxWidgets-инфраструктуры для ZIP-потоков.

Будущая поддержка может включать:

- PK3 / ZIP;
- архивы-каталоги;
- GRP;
- PAK;
- другие ресурсные контейнеры семейства Doom.

Добавление второго формата должно происходить после стабилизации
WAD-пути и обобщения `ArchiveSession`/archive API.

## 8. Архитектура Kotlin ↔ native

Текущая граница:

```text
Android UI
   │
   ▼
SladeNative / Kotlin API
   │
   ▼
JNI
   │
   ▼
native-lib.cpp
   │
   ▼
ArchiveSession
   │
   ▼
SLADE headless core
```

`ArchiveSession` — текущая нативная абстракция над открытым WAD и его
состоянием редактирования. Она пока жёстко типизирована на `WadArchive*`.

## 9. Модель многопоточности

Тяжёлые нативные операции не выполняются непосредственно в UI-потоке.

`SladeNative.kt` использует один выделенный background executor:

```text
UI thread
   │
   ▼
single native executor
   │
   ▼
JNI / ArchiveSession
   │
   ▼
SLADE
```

Последовательное выполнение выбрано намеренно: текущая `ArchiveSession`
хранит изменяемое состояние и не рассчитана на произвольный параллельный
доступ.

Отмена coroutine-задачи может убрать ещё не начавшийся queued-вызов, но
не прерывает уже выполняющийся блокирующий native-вызов.

## 10. Работа с файлами Android

Приложение использует Android Storage Access Framework (SAF).

Текущий путь входных данных:

```text
SAF Uri
   ↓
ParcelFileDescriptor
   ↓
raw file descriptor
   ↓
native fstat / mmap
   ↓
MemChunk
   ↓
WadArchive
```

Архив не передаётся через промежуточный Kotlin `ByteArray`. При этом
архитектура не является полностью zero-copy: отображённые данные всё ещё
копируются в `MemChunk` SLADE.

Владение raw fd после `detachFd()` передаётся native-коду, который отвечает
за его закрытие.

## 11. Текущие возможности редактирования WAD

Текущий WAD MVP поддерживает:

- открытие и просмотр WAD;
- перечисление entries;
- базовый preview поддерживаемых ресурсов;
- переименование;
- удаление;
- перемещение;
- экспорт;
- добавление;
- замену;
- Save As;
- Save в исходный документ для разрешённых PWAD;
- Discard Changes;
- отслеживание dirty state.

Основные операции подтверждены через цикл:

```text
Open → Edit → Save/Save As → Close → Reopen → Verify
```

## 12. Конвейер сохранения

### Save As

Save As записывает результат в новый файл, выбранный через SAF
`ACTION_CREATE_DOCUMENT`. Исходный документ при этом не открывается на
запись.

### Save in-place

Для сохранения в исходный документ используется двухшаговый протокол:

1. `nativeValidateForSave()` сериализует текущую сессию в памяти и
   переоткрывает результат как независимый `WadArchive`, сверяя структуру
   и число entries.
2. Только после успешной валидации Kotlin открывает исходный URI в режиме
   `"rwt"`.
3. `nativeCommitSave(fd)` записывает уже провалидированный результат.

Это сильнее простой прямой записи: исходный файл не затрагивается до
завершения валидации сериализации.

Однако это **не атомарная замена файла**. `"rwt"` может усечь исходный
файл в момент открытия, поэтому убийство процесса между открытием fd и
завершением записи теоретически может оставить оригинал повреждённым.
Настоящая atomic rename поверх произвольного `content://` URI не является
гарантией, которую приложение может предоставить через SAF.

Настоящая rollback/atomic replacement схема остаётся отдельной областью
для будущего улучшения, если это позволит конкретный SAF provider.

### IWAD protection

Save in-place намеренно блокируется для распознанных IWAD. Для таких
файлов используется Save As.

### Discard Changes

Discard закрывает/сбрасывает текущие несохранённые изменения без записи
в исходный файл.

## 13. Слой предварительного просмотра ресурсов

Нативный мост сейчас обрабатывает, среди прочего:

- необработанные данные entries;
- текстовые preview;
- PNG-данные;
- palette preview;
- flat 64×64;
- Doom graphic/patch decoding;
- определение и разбор метаданных аудио для нескольких форматов.

PNG декодируется на Android после передачи PNG-данных из native-кода.

Полноценные редакторы ресурсов и аудиоплеер относятся к будущим этапам.

## 14. Определение типа записи

Сейчас используется временный Android-side классификатор типов записей.

Цель — по мере портирования необходимых компонентов перейти к единой
семантике SLADE `EntryType` и не поддерживать две независимые системы
классификации.

Текущий классификатор ориентирован на WAD и не является готовой моделью
для PK3/ZIP с путями и расширениями.

### Kotlin / Android

- диалоги;

### SLADE

Отвечает за переиспользуемую доменную логику архивов и ресурсов и знания
о форматах, которые могут работать без desktop UI.

## 16. Архитектурные ограничения

### Одна активная сессия

Текущая реализация рассчитана на одну активную archive session. В будущем
архитектура может развиться в менеджер документов/сессий.

### WAD-first

`ArchiveSession` пока конкретно работает с `WadArchive*`. Для PK3/ZIP
потребуется абстракция над конкретным типом контейнера.

### Размеры

На Kotlin размеры файлов следует хранить в `Long`. В native API нужно
избегать без необходимости 32-битных размеров/смещений там, где возможны
большие файлы.

## 17. Planned structural refactoring

Текущая архитектура постепенно движется к:

```text
Activity
   ↓
ArchiveViewModel / UI State
   ↓
ArchiveRepository / application layer
   ↓
SladeNative
   ↓ JNI
Native adapter
   ↓
ArchiveSession / SavePipeline / EntryData
   ↓
SLADE core
```

Рефакторинг выполняется extraction-подходом, без переписывания работающего
WAD MVP с нуля.

Контрольные этапы:

```text
R0  Baseline / regression protection
R1  Kotlin state separation
R2  Native/JNI separation
R3  Archive API
R4  Typed data contract
R5  Compatibility layer cleanup
R6  Save pipeline isolation
R7  Undo/Redo command foundation
R8  Native tests / CI
R9  Performance profiling
R10 PK3/ZIP readiness
```

Подробный порядок работ находится в `documents/REFACTORING.md`.

## 19. Приоритеты разработки

1. Сохранять отзывчивость Android UI.
2. Держать native archive operations изолированными от UI.
3. Явно контролировать ownership `ArchiveSession`.
4. Использовать SLADE domain logic вместо дублирования там, где это уже
   возможно.
5. Держать compatibility shims небольшими и документированными.
6. Зафиксировать regression baseline до крупных структурных изменений.
7. Сначала стабилизировать WAD workflow и save validation, затем расширять
   архитектуру на новые форматы.
8. Добавлять новые редакторы после прохождения соответствующих этапов
   структурного рефакторинга.
