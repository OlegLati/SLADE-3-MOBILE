## 1. Идентификация проекта
**Проект:** SLADE 3 Mobile
**Назначение:** Android-приложение для просмотра и редактирования
ресурсных архивов семейства Doom с использованием SLADE 3 в качестве
нативного бэкенда для работы с архивами и ресурсами.

**Текущая база SLADE:** SLADE 3.3.0 Beta 2

Это не буквальный порт настольного приложения на Android.
Пользовательский интерфейс Android, работа с файлами, жизненный цикл,
многопоточность и интеграция с платформой реализованы нативно для
Android, тогда как выбранные компоненты SLADE без графического
интерфейса повторно используются через C++.

## 2. Среда разработки
### Основная IDE для разработки

Официальный репозиторий:

настольной ОС.

## 5. Система нативной сборки
Нативный код собирается через Android Gradle Plugin + CMake + NDK.

Точка входа:

``` text
app/src/main/cpp/CMakeLists.txt
```

В результате нативной сборки создаются:

``` text
slade_core  — STATIC
myapplication — SHARED
```

### `slade_core`
`slade_core` --- выбранный слой SLADE для работы с архивами и разбора
данных без настольного UI. Текущие исходники включают:

``` text
Archive/Archive.cpp
Archive/ArchiveDir.cpp
Archive/ArchiveEntry.cpp
Archive/ArchiveManager.cpp
Archive/Formats/WadArchive.cpp

Utility/StringUtils.cpp
Utility/FileUtils.cpp
Utility/Tokenizer.cpp
Utility/MemChunk.cpp
Utility/Parser.cpp
Utility/Tree.cpp
```

Компоненты настольного интерфейса и другие части, сильно зависящие от
wxWidgets/OpenGL, намеренно исключены.

### `myapplication`
`myapplication` --- JNI-мост, загружаемый из Kotlin:

``` kotlin
System.loadLibrary("myapplication")
```

Он связывает `slade_core` с Android-частью и предоставляет нативные
операции, доступные приложению.

## 6. Интеграция исходного кода SLADE
Исходный код SLADE хранится непосредственно в проекте по пути:

``` text
app/src/main/cpp/third_party/SLADE/
```

Текущая схема выглядит так:

``` text
Исходный код SLADE
    ↓
выбранные компоненты без desktop UI
    ↓
слой совместимости с Android
    ↓
slade_core
    ↓
JNI-мост
    ↓
Kotlin Android UI
```

Проект намеренно не собирает полноценное настольное приложение SLADE.

### Слой совместимости
Android-специфичный код совместимости находится в:

``` text
app/src/main/cpp/compat/
```

Важные файлы:

``` text
android_compat.h
common.h
common2.h
slade_shims.cpp
```

Слой совместимости должен оставаться тонким. Он не должен превращаться
во вторую независимую реализацию SLADE.

## 7. Текущий охват архивных форматов
Текущий нативный слой работы с архивами в первую очередь ориентирован на
**WAD**.

`ZipArchive.cpp` намеренно исключён, поскольку настольная реализация
зависит от классов wxWidgets для ZIP-потоков. Для будущей поддержки
PK3/ZIP потребуется совместимая с Android реализация ZIP/контейнера либо
изолированный слой совместимости.

Потенциальная будущая поддержка контейнеров:
- PK3 / ZIP
- архивы-каталоги
- GRP
- PAK
- другие ресурсные контейнеры семейства Doom

## 8. Архитектура Kotlin ↔ native
Концептуально:

``` text
Android UI
   │
   ▼
SladeNative / Kotlin API
   │
   ▼
JNI
   │
   ▼
native-lib.cpp
   │
   ▼
ArchiveSession
   │
   ▼
SLADE headless core
```

`ArchiveSession` --- текущая нативная абстракция над открытым архивом.
Сейчас она ориентирована на WAD и отслеживает состояние
редактирования/изменённости.

## 9. Модель многопоточности
Тяжёлые нативные операции с архивами не должны выполняться
непосредственно в UI-потоке Android.

Текущая граница использует однопоточный исполнитель для нативных
операций:

``` text
UI thread
   │
   ▼
single native executor
   │
   ▼
JNI / ArchiveSession
   │
   ▼
SLADE
```

Последовательное выполнение выбрано намеренно, поскольку текущая сессия
архива хранит изменяемое состояние и пока не рассчитана на произвольный
параллельный доступ.

## 10. Работа с файлами Android
Приложение использует Android Storage Access Framework (SAF).

Текущий путь входных данных:

``` text
SAF Uri
   ↓
ParcelFileDescriptor
   ↓
raw file descriptor
   ↓
native fstat / mmap
   ↓
MemChunk
   ↓
WadArchive
```

Это позволяет не передавать весь архив через промежуточный `ByteArray` в
Kotlin. При этом текущая архитектура всё ещё копирует отображённые в
память входные данные в `MemChunk` SLADE.

## 11. Текущие возможности редактирования WAD
Проект сейчас содержит основу для:
- открытия WAD-архивов
- просмотра записей
- предварительного просмотра/доступа к данным записей
- переименования
- удаления
- экспорта
- замены
- добавления
- Save As
- отслеживания состояния изменённости

Текущий путь сохранения следует рассматривать как **Save As / запись в
явно выбранное место назначения**, а не как полноценную систему
безопасной замены исходного файла с защитой от сбоев.

## 12. Слой предварительного просмотра ресурсов
Нативный мост сейчас обрабатывает несколько форматов Doom/ресурсов,
включая:
- необработанные данные записи
- предварительный просмотр текста
- передачу данных PNG
- предварительный просмотр палитры
- декодирование flat 64×64
- классическое декодирование графики/patch Doom
- определение и разбор метаданных аудио для нескольких форматов

Декодирование PNG сейчас выполняется на Android после передачи данных
PNG из native-кода.

Воспроизведение аудио и полноценные редакторы ресурсов являются
отдельными пунктами дорожной карты.

## 13. Определение типа записи
В проекте сейчас используется временный самописный классификатор типов
записей.

Долгосрочная цель --- по возможности использовать собственную систему
`EntryType` SLADE, чтобы семантика Android и настольной версии
оставалась согласованной.

Android-специфичный классификатор не должен превращаться во вторую
постоянную систему типов.

## 14. Ответственность компонентов платформы
### Kotlin / Android
Отвечает за:
- Activity и жизненный цикл Android
- UI
- отображение списков через RecyclerView
- выбор файлов через SAF
- диалоги и взаимодействие с пользователем
- декодирование изображений на стороне Android
- оркестрацию корутин/исполнителей

### C++
Отвечает за:
- разбор архивов
- редактирование архивов
- доступ к данным записей
- декодирование ресурсов Doom там, где это необходимо
- работу с нативной памятью
- интеграцию SLADE
- JNI-мост

### SLADE
Отвечает за повторно используемую доменную логику архивов и ресурсов, а
также знания о форматах семейства Doom, которые могут работать без
настольного UI.

## 15. Архитектурные ограничения
### Одна активная сессия
Текущая реализация рассчитана на одну активную сессию архива. Для MVP
этого достаточно, однако в дальнейшем архитектура должна развиться в
менеджер документов/сессий с поддержкой нескольких открытых архивов.

### Ограничения 32-битных размеров
Некоторые текущие интерфейсы всё ещё используют 32-битные типы
размеров/смещений. Размеры файлов на стороне Kotlin следует предпочитать
хранить в `Long`, а в нативных интерфейсах использовать типы целого
числа соответствующего размера там, где требуется поддержка больших
файлов.

### Реализация WAD-first
Архитектура намеренно развивается от WAD. PK3/ZIP и другие контейнеры
следует добавлять после стабилизации редактирования WAD и безопасного
сохранения.

## 15.1. Planned structural refactoring

Текущий код уже работает как WAD MVP, но следующие крупные изменения должны
проводиться через постепенное разделение ответственности.

Целевой поток:

``` text
Activity
   ↓
ArchiveViewModel
   ↓
ArchiveRepository
   ↓
SladeNative
   ↓ JNI
Native adapter
   ↓
ArchiveSession / SavePipeline / EntryData
   ↓
SLADE core
```

Крупные текущие файлы не следует переписывать целиком. Рекомендуется
последовательный extraction с обязательной проверкой Open → Edit → Save →
Reopen после каждого крупного шага.

Подробный план находится в:

``` text
documents/REFACTORING.md
```

## 17. Приоритеты разработки
При внесении архитектурных изменений:
1. Сохранять отзывчивость Android UI.
2. Держать нативные операции с архивами изолированными от UI.
3. Явно контролировать владение `ArchiveSession`.
4. По возможности использовать настоящую логику форматов/предметной
    области SLADE вместо дублирования Android-специфичных реализаций.
5. Делать compatibility shims небольшими и документированными.
6. Добавить нативные тесты до масштабного расширения редакторов.
7. Реализовать безопасное сохранение/валидацию до деструктивной
    перезаписи.
8. Добавлять новые форматы архивов только после стабилизации WAD-пути.

## 18. Контрольный список проверки
Перед тем как считать изменение нативной/архивной части завершённым:

``` text
[ ] Синхронизация проекта проходит успешно
[ ] Нативный C++ код успешно компилируется
[ ] Приложение запускается на целевом устройстве с API 24+
[ ] WAD успешно открывается
[ ] Список записей остаётся целостным
[ ] Границы данных записей проверяются
[ ] Редактирование не блокирует UI
[ ] Изменённый архив можно сохранить
[ ] Сохранённый архив можно повторно открыть
[ ] Неизменённые записи остаются целыми
[ ] Повреждённый/обрезанный входной файл обрабатывается безопасно
```

Для функций редактора наиболее сильным интеграционным тестом является:

``` text
Open → Modify → Save → Close → Reopen → Verify
```
