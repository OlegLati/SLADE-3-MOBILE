## 1. Обзор

SLADE Mobile — Android-приложение для просмотра и редактирования Doom/WAD-ресурсов, использующее выбранные headless-компоненты SLADE 3 как нативное ядро.

Проект не переносит настольный интерфейс SLADE на Android. Android UI, жизненный цикл, SAF и пользовательские сценарии реализуются отдельно.

Базовая схема:

```text
SLADE Core
    ↓
Native adapter / JNI
    ↓
SladeNative.kt
    ↓
Android UI
```

## 2. Цели

Основные цели:

- стабильное редактирование WAD на Android;
- открытие, просмотр и предварительный просмотр записей;
- rename, delete, move, add, replace и export;
- Save As и сохранение исходного документа после валидации;
- постепенное отделение UI от состояния и нативной предметной логики;
- подготовка архитектуры к нескольким форматам архивов и редакторам ресурсов.

PK3/ZIP, полноценные редакторы ресурсов, поиск, Undo/Redo и редактор карт относятся к последующим этапам.

## 3. Не входящие в текущую задачу направления

Проект не должен:

- переносить wxWidgets;
- копировать desktop UI SLADE;
- переносить ненужную desktop-инфраструктуру;
- превращать `compat/` в самостоятельную замену SLADE;
- добавлять абстракции без реального потребителя.

## 4. Текущая архитектура

Фактическая реализация текущего MVP:

```text
MainActivity / Android UI
        ↓
SladeNative.kt
        ↓
JNI / native-lib.cpp
        ↓
ArchiveSession
        ↓
WadArchive
        ↓
SLADE headless core
```

`ArchiveSession` уже существует, но сейчас жёстко ориентирована на WAD: внутри хранится `MemChunk*` и `WadArchive*`, а не универсальный `Archive*`.

`SladeNative.kt` использует один выделенный поток для всех native-вызовов. Это сохраняет последовательный доступ к изменяемому native-состоянию.

## 5. Целевая архитектура

Структурный рефакторинг постепенно должен привести к:

```text
Android UI
    ↓
ViewModel / UI State
    ↓
Archive Repository / application layer
    ↓
SladeNative / JNI
    ↓
Native adapter
    ↓
ArchiveSession / ArchiveOperations / SaveService
    ↓
SLADE Core
```

`ViewModel`, `Repository`, `ArchiveOperations` и отдельный `SaveService` — целевые компоненты. Их наличие не следует считать фактом текущего кода до соответствующего этапа рефакторинга.

## 6. Разделение ответственности

### Android / Kotlin

Отвечает за:

- Activity и жизненный цикл;
- UI и диалоги;
- SAF;
- состояние пользовательского интерфейса;
- запуск фоновых операций;
- преобразование результатов native API в UI-модели.

### JNI / native adapter

Отвечает за:

- преобразование аргументов и результатов JNI;
- работу с file descriptor;
- границу Android ↔ C++;
- передачу вызовов в нативные сервисы.

JNI не должен становиться местом хранения основной бизнес-логики архива.

### Нативный слой

Отвечает за:

- ArchiveSession;
- операции с архивом;
- сериализацию;
- валидацию сохранения;
- чтение данных записей;
- нативное декодирование ресурсов.

### SLADE Core

Отвечает за повторно используемую доменную логику архивов и ресурсов, когда соответствующие компоненты не зависят от desktop UI.

## 7. ArchiveSession

`ArchiveSession` представляет открытый редактируемый документ.

Текущая модель:

```text
ArchiveSession
 ├── исходные данные / MemChunk
 ├── WadArchive
 └── dirty state
```

В будущем сессия должна быть отвязана от `WadArchive` настолько, чтобы один и тот же application layer мог работать с WAD, ZIP/PK3 и другими контейнерами.

На текущем этапе допустима одна активная сессия.

## 8. Работа с файлами

Входной путь:

```text
SAF Uri
   ↓
ParcelFileDescriptor
   ↓
raw file descriptor
   ↓
native fstat / mmap
   ↓
MemChunk
   ↓
WadArchive
```

Большой архив не передаётся через промежуточный Kotlin `ByteArray` целиком.

## 9. mmap и копирование данных

`mmap` используется для уменьшения лишних копирований при чтении файла.

Архитектура **не является zero-copy**:

```text
mmap
  ↓
MemChunk
```

Отображённые данные могут копироваться в структуры SLADE. Полный zero-copy не является текущей целью.

## 10. Многопоточность

Тяжёлые операции не выполняются непосредственно в UI-потоке.

Текущая схема:

```text
UI thread
    ↓
один native executor
    ↓
JNI / ArchiveSession
    ↓
SLADE
```

Один поток выбран потому, что текущая `ArchiveSession` содержит изменяемое состояние и не рассчитана на произвольный параллельный доступ.

## 11. Жизненный цикл нативных ресурсов

Для `mmap`, `MemChunk`, `WadArchive` и других native-объектов должен соблюдаться предсказуемый жизненный цикл:

```text
open → use → close → free
```

Нельзя допускать утечек памяти, двойного освобождения, висячих указателей и использования уже освобождённых объектов.

## 12. Структурный рефакторинг

Рефакторинг начинается после получения работающего WAD MVP и выполняется извлечением существующих ответственностей.

Порядок контрольных этапов:

```text
R0  Baseline и защита от регрессий
R1  Разделение Kotlin UI и состояния
R2  Разделение JNI и native domain
R3  Унификация Archive API
R4  Типизированный контракт данных
R5  Очистка compatibility layer
R6  Выделение save pipeline
R7  Основа Undo / Redo
R8  Ручная WAD-регрессия
R9  Профилирование производительности
R10 Подготовка к PK3/ZIP
```

Главное правило: структурное изменение не должно одновременно менять поведение без необходимости.

## 13. Типы записей

Сейчас используется временный `androidDetectEntryType()`.

Целевое состояние:

```text
SLADE EntryType
      ↓
единая семантика типов
      ↓
Android
```

Текущая эвристика пригодна для WAD, но не должна становиться второй постоянной системой типов при появлении PK3/ZIP.

## 14. Архитектура редакторов

Целевая схема:

```text
Entry
  ↓
EntryType
  ↓
EditorRegistry
  ├── TextEditor
  ├── ImageEditor
  ├── GraphicEditor
  ├── PaletteEditor
  ├── TextureEditor
  ├── AudioEditor
  ├── HexEditor
  └── MapEditor
```

Браузер архива не должен знать внутреннюю реализацию конкретного редактора.

## 15. Данные и представление

Нативный слой должен отдавать данные, а не строить Android UI.

Целевая модель:

```text
Entry
  ↓
EntryData
  ↓
Kotlin
  ↓
подходящий редактор
```

Специализированные методы вроде `entryPng()` допустимы на текущем прототипном этапе, но при дальнейшем рефакторинге граница должна становиться более типизированной и общей.

## 16. Операции редактирования

Текущие операции:

```text
add
remove
rename
move
replace
export
```

Проверки выполняются через обычный Android UI и проходят через `ArchiveSession`; тестовые WAD не должны изменять исходные fixture-файлы.

## 17. Конвейер сохранения

### Save As

```text
ArchiveSession
    ↓
сериализация в память
    ↓
валидация
    ↓
SAF CreateDocument
    ↓
запись нового файла
```

### Сохранение исходного документа

```text
ArchiveSession
    ↓
сериализация в память
    ↓
валидация
    ↓
SAF openFileDescriptor("rwt")
    ↓
commit проверенных байтов
```

Валидация должна завершиться **до** открытия исходного документа в `rwt`.

Текущий путь не является атомарной заменой файла: SAF не предоставляет здесь реализованный проектом atomic replace. При прерывании после `rwt` исходный файл может оказаться обрезанным или частично записанным.

## 18. Undo / Redo

Целевая модель строится вокруг команд:

```text
Command
 ├── Rename
 ├── Replace
 ├── Add
 ├── Delete
 └── Move
```

Полная история команд в текущем MVP ещё не реализована.

## 19. Мобильный интерфейс

UI проектируется отдельно от desktop SLADE и должен учитывать touch, небольшие экраны, планшеты, portrait/landscape, long press и жесты.

## 20. Надёжность и безопасность

Любой входной архив следует считать потенциально повреждённым.

Для бинарных данных необходимо проверять:

- смещения;
- размеры;
- количество записей;
- границы файла;
- размеры ресурсов;
- структуру каталога.

## 21. Тестирование

Базовый интеграционный сценарий:

```text
Open → Modify → Save → Close → Reopen → Verify
```

Для native-слоя необходимы fixture-файлы как минимум для нормального, пустого, большого, обрезанного и повреждённого WAD.

Нативные автоматизированные тесты являются отдельной задачей текущего структурного этапа.

## 22. Производительность

Сначала фиксируются ownership, lifecycle и границы API. После этого узкие места измеряются профилировщиком.

Только измеренные проблемы становятся основанием для оптимизации памяти, mmap, lazy loading или дополнительных native-копий.

## 23. Расширяемость

Целевая модель:

```text
Archive
 ├── WAD
 ├── ZIP
 ├── PK3
 └── другие форматы
```

Добавление формата не должно требовать переписывания Android UI или браузера архива.

## 24. Итоговая архитектурная цель

Конечная модель проекта:

```text
Open Archive
     ↓
Browse
     ↓
Preview / Edit
     ↓
Validate
     ↓
Save
     ↓
Reopen / Verify
```

Android должен оставаться пользовательским слоем, а SLADE — повторно используемым нативным ядром там, где его компоненты подходят для headless-использования.
