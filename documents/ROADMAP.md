# SLADE Mobile — дорожная карта разработки

> Актуальная дорожная карта проекта. Документ описывает фактическое состояние WAD MVP и следующий структурный этап. Все тексты в каталоге `documents/` ведутся на русском языке.

## Текущее состояние проекта

**Завершено:**

- базовая Android-сборка и нативная интеграция;
- интеграция выбранного headless-кода SLADE;
- Android SAF → file descriptor → native path;
- WAD browser;
- preview поддерживаемых ресурсов;
- `ArchiveSession`;
- rename;
- delete;
- move;
- add;
- replace;
- export;
- dirty state;
- Save As;
- валидация перед сохранением;
- сохранение в исходный документ через `validate → commit`;
- Discard Changes;
- вертикальные WAD-сценарии Slice 1–3.

**Текущий этап:**

> **Phase 8.5 — структурный рефакторинг.**

Главные следующие задачи — R0–R10 из `REFACTORING.md`, прежде всего baseline/regression protection, разделение Kotlin state, разделение JNI и native domain, а затем native tests и основа Undo/Redo.

## Важные ограничения текущей версии

1. Текущий native archive path ориентирован на WAD.
2. `ArchiveSession` пока хранит `MemChunk*` + `WadArchive*`.
3. `ZipArchive.cpp` не включён в Android native build из-за зависимости desktop-кода от wxWidgets ZIP streams.
4. `androidDetectEntryType()` является временной WAD-ориентированной эвристикой.
5. Сохранение в исходный файл не является атомарной заменой: `rwt` может обрезать исходный документ до записи новых байтов.
6. Save As создаёт отдельный файл через SAF и не имеет этого же риска для исходного документа.
7. `ViewModel`, `Repository`, универсальный `Archive` API и отдельный `SaveService` являются целевой архитектурой, а не текущими компонентами.

# Phase 4 — определение типа записи

**Статус: ЧАСТИЧНО ЗАВЕРШЕНО**

Текущая реализация достаточна для WAD MVP, но не является полной системой типов SLADE.

---

# Phase 5 — фоновые операции

**Статус: ЗАВЕРШЕНО для текущего MVP**

Все native-вызовы Kotlin проходят через один выделенный background executor.

Текущий контракт использует `NativeResult`.

Отмена тяжёлой уже выполняющейся native-операции пока не является полноценной cooperative cancellation и остаётся отдельной задачей.

---

# Phase 6 — ArchiveSession

**Статус: ЗАВЕРШЕНО для WAD**

`ArchiveSession` уже владеет состоянием открытого WAD и отслеживает изменения.

Текущая структура WAD-специфична. Форматно-независимая сессия появится только при наличии реального второго контейнера.

# Phase 8 — Safe Save

**Статус: ЗАВЕРШЕНО**

## 8.1. Save As

```text
изменённая сессия
 ↓
сериализация в память
 ↓
валидация
 ↓
SAF CreateDocument
 ↓
новый файл
```

## 8.2. Сохранение в исходный документ

```text
изменённая сессия
 ↓
validateForSave()
 ↓
сериализация + независимая проверка в памяти
 ↓
openFileDescriptor("rwt")
 ↓
commitSave(fd)
```

Валидация выполняется до открытия исходного документа в `rwt`.

## 8.3. Ограничение атомарности

Это **не atomic replace**.

После открытия исходного документа в `rwt` прерывание записи может оставить исходный файл обрезанным или частично записанным. Это ограничение текущего SAF-пути и должно оставаться явно указанным во всех документах, описывающих сохранение.

## 8.4. Discard Changes

Discard восстанавливает native-сессию из исходных данных без записи изменений на диск.

# Definition of Done для текущего MVP

WAD Editor MVP считается завершённым, если:

- проект собирается;
- WAD открывается;
- entries отображаются;
- preview работает для поддерживаемых типов;
- Rename/Delete/Move/Add/Replace работают;
- Export работает;
- Save As работает;
- сохранение в исходный документ проходит через `validate → commit`;
- Discard работает;
- сохранённый WAD можно повторно открыть;
- текущее ограничение неатомарного in-place save явно задокументировано.

## Definition of Done для структурного рефакторинга

Рефакторинг считается завершённым поэтапно, когда:

- каждый вынесенный слой имеет одну понятную ответственность;
- существующий WAD MVP проходит regression slice;
- JNI не содержит основной domain logic;
- ownership native-данных очевиден;
- save pipeline имеет отдельную понятную границу;
- native tests выполняются автоматически;
- документация совпадает с кодом.

# Контрольная последовательность разработки

Каждое значимое изменение проходит:

```text
1. Изменить код
2. Собрать
3. Проверить целевой сценарий
4. Запустить regression slice
5. Обновить документацию при изменении архитектурного поведения
6. Сделать небольшой коммит
```

Для структурного рефакторинга предпочтительны отдельные feature/refactoring-ветки.

# Источник истины

При расхождениях между документами порядок интерпретации текущего состояния:

1. фактический код и сборочная конфигурация;
2. `documents/TECHNICAL.md` — техническая реализация;
3. `documents/DESIGN.md` — текущая и целевая архитектура;
4. `documents/ROADMAP.md` — статусы и порядок работ;
5. `documents/REFACTORING.md` — план структурной миграции;
6. `README.md` и `README_ENG.md` — пользовательское резюме.

Если код и документация расходятся, сначала исправляется документация, если код уже является намеренным текущим поведением; если намерение меняется — сначала меняется код и затем документация.
